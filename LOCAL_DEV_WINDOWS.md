# Running Holiday Vibez CRM locally on Windows

The main setup lives in [README.md](README.md#getting-started). This file only
covers the Windows-specific gotchas that will otherwise block a first run. It
was written after a clean bring-up on Windows 10 (Node 24, no Docker, embedded
Postgres).

The stack is three processes:

| Process           | Port | Started by                          |
| ----------------- | ---- | ----------------------------------- |
| Embedded Postgres | 5433 | `node scripts/dev-db.js` (in `apps/api`) |
| API (NestJS)      | 4100 | `npm run dev:api`                   |
| Web (Next.js)     | 3000 | `npm run dev:web`                   |

The web server proxies `/api` and `/uploads` to the API (see
`apps/web/next.config.js`), so the browser only ever talks to `http://localhost:3000`.

---

## Quick start (Windows, no Docker)

From the repo root, once (`npm install` obeys `.npmrc`'s `ignore-scripts=true`,
so Prisma's client must be generated by hand):

```bash
npm install
npm run build:shared
npx prisma generate --schema apps/api/prisma/schema.prisma
```

Set up `apps/api/.env` (copy from `apps/api/.env.example`) with these
Windows-friendly values — see the notes below for why:

```dotenv
DATABASE_URL="postgresql://holidayvibez:holidayvibez@127.0.0.1:5433/holiday_vibez_crm?connection_limit=10"
PORT=4100
# REDIS_URL left unset on purpose — see note 2
```

Then, in three terminals:

```bash
# terminal 1 — database (leave running)
cd apps/api && node scripts/dev-db.js
```

```bash
# terminal 2 — apply migrations + seed (first run only), then the API
npm run migrate    # or: npx prisma migrate deploy --schema apps/api/prisma/schema.prisma
npm run seed       # skip if the database already has data
npm run dev:api
```

```bash
# terminal 3 — web
npm run dev:web
```

Open http://localhost:3000 and sign in with a seeded account:

- `admin@holidayvibez.com` / `Password@123` (Admin)
- `director@holidayvibez.com` / `Password@123` (Director)

## The Windows-specific issues, and the fixes

### 1. Embedded Postgres won't start — `dynamic_shared_memory_type = posix`

**Symptom:** `node scripts/dev-db.js` exits immediately with:

```
FATAL:  invalid value for parameter "dynamic_shared_memory_type": "posix"
HINT:   Available values: windows.
```

`embedded-postgres`'s `initdb` writes `dynamic_shared_memory_type = posix` into
the generated `.pgdata/postgresql.conf`, but POSIX shared memory doesn't exist
on Windows.

**Fix:** handled automatically. `scripts/dev-db.js` now rewrites that setting to
`windows` before starting the server (Windows-only, idempotent). Nothing to do
by hand. If you ever wipe `.pgdata` and re-init, it's re-applied on the next
start.

### 2. API hangs on boot (background jobs need Redis)

**Symptom:** the API logs `Starting Nest application...`, maps every route, then
never prints `Holiday Vibez API listening on :4100` and never accepts requests.

The background-jobs module (BullMQ) is loaded only when `REDIS_URL` is set
(`apps/api/src/app.module.ts`). When it's set but no Redis is reachable, the
scheduler's `onModuleInit` awaits a Redis connection forever and bootstrap never
completes. `redis-memory-server` (the `scripts/dev-redis.js` helper) has no
reliable Windows binary, so there's usually no local Redis to connect to.

**Fix:** leave `REDIS_URL` **unset** in `apps/api/.env`. The app then skips the
jobs module and boots normally. The trade-off is that scheduled cron jobs (SLA
sweeps, birthday/occasion greetings, currency refresh, compliance checks, etc.)
don't run — none of which are needed to develop or click through the app. To run
them, point `REDIS_URL` at a real Redis (e.g. WSL2, a container, or a managed
instance) and restart the API.

### 3. Prisma `P2037: too many clients already`

**Symptom:** the API crashes on boot with:

```
PrismaClientInitializationError: Too many database connections opened:
FATAL: sorry, too many clients already   (errorCode: 'P2037')
```

Prisma's default connection pool is `num_cpus * 2 + 1` connections. On a
many-core machine, a couple of `nest start --watch` reloads (each opening a
fresh pool before the old process's connections are reaped) can exhaust
embedded Postgres's `max_connections = 100`.

**Fix:** cap the pool by adding `?connection_limit=10` to `DATABASE_URL` in
`apps/api/.env` (shown in the Quick start above). If you've already exhausted
the connections, either restart `scripts/dev-db.js`, or terminate the idle ones:

```bash
# from apps/api, with the DB running
node -e "const{PrismaClient}=require('@prisma/client');const p=new PrismaClient();p.\$queryRawUnsafe(\"SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='holiday_vibez_crm' AND pid <> pg_backend_pid()\").then(r=>console.log('terminated',r.length)).finally(()=>p.\$disconnect())"
```

### 4. API `Cannot find module './auth/auth.module'` from `dist/`

**Symptom:** the API compiles with `Found 0 errors` but then crashes at runtime:

```
Error: Cannot find module './auth/auth.module'
  ... at apps/api/dist/app.module.js
```

This happens when a stale `apps/api/tsconfig.tsbuildinfo` (TypeScript's
incremental-build cache) is present without a matching `dist/` — e.g. after
copying/transferring the repo rather than a clean `git clone`. The incremental
build trusts the cache, thinks everything is already emitted, and only re-emits
a subset, leaving `dist/` with missing modules.

**Fix:** delete both and let it rebuild from scratch:

```bash
# from apps/api
rm -rf dist tsconfig.tsbuildinfo
npm run dev:api
```

(Both are git-ignored, so this never affects committed files.)

## Stopping everything

Ctrl-C each terminal, or free the ports:

```bash
npx --yes kill-port 3000 4100 5433
```
